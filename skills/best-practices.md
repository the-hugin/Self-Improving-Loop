---

## Как читать этот журнал

**При старте проекта:** найди записи с похожим стеком — там готовые паттерны для переиспользования.
**При проектировании:** поищи по тегам решения, которые уже доказали эффективность.
**При ревью:** проверь, не изобретаешь ли велосипед — может, паттерн уже зафиксирован.


---

## Правила ведения

- **Только проверенное.** Не добавляй "кажется хорошей идеей" — только то, что уже дало результат.
- **Паттерн должен быть переносимым.** Если применим только к одному проекту — не стоит записывать.
- **Конкретность важнее полноты.** Код-сниппет лучше абстрактного описания.
- **Не редактируй старые записи.** Если паттерн эволюционировал — добавь новую запись со ссылкой.
- **Теги помогают поиску.** Используй стек (python, react, sqlite), тип (arch, perf, ux, prompt) и домен (api, ui, db, llm).

## [2026-03-04] — [PROJECT] — Two-axis severity вместо single-score threshold

**Теги:** arch, scoring, alerting, python

Контекст:   Система детекторов генерировала слишком много CRITICAL алертов при одном сильном детекторе.
Паттерн:    Severity определяется двумя независимыми осями: `score >= N AND detector_count >= M`. Одна ось без другой = не CRITICAL. Это предотвращает корреляционные false positives когда два детектора всегда срабатывают вместе.
Результат:  20 из 23 CRITICAL алертов стали HIGH после введения двухосевой модели — точность выросла.
Применимо:  Любая система scoring где несколько сигналов могут коррелировать (fraud detection, anomaly detection, monitoring).
